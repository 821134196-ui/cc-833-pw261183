# 有且只有一个所有者 · 小型控制器沙盘

一个从零实现的小型控制器，管理**带版本号的任务资源**。重点是两件容易同时出错的事：

1. **乱序事件不能让对象复活**：旧实例已经发出创建指令，新实例却先读到删除事件。
2. **交接不能让旧实例领取的活变成孤儿**：断线/重启后，旧实例手上的任务必须有明确归宿。

实现用本地模拟的 API Server，不依赖任何外部服务，也不需要安装依赖。

## 运行

```bash
npm start          # http://127.0.0.1:4173/
npm test           # 13 个不变量与场景测试（Node 内置 test runner）
npm run drill      # 命令行版「同一次断线检验」，打印两种策略的结论
```

Node ≥ 20。

## 页面能做什么

- **API Server 面板**：资源版本、事件日志、每个事件投递给了哪些实例；可**暂停投递**、
  **单步一个**、或点某一行的按钮只把该事件投给指定实例（制造乱序）。
- **故障注入**：按题目时序手动走一遍——旧实例发出 `create task/ghost` → 管理员删除它 →
  删除 `task/b` → 新建 `task/c` → 新实例从旧检查点上线。也可一键「按题目时序自动播放」。
- **控制器实例**：断线、重连、协调一次、干一格、提升为活跃；点击卡片切换观察对象。
- **最终持有者**：只看服务器接受的写入；标出「无主」「离线」「无人执行」与所有者数量。
- **交接台账**：断线时挂起的每项任务，最终交给了谁；未决会标红。
- **时序回放**：同一条故障脚本的逐拍快照，红色描边=有任务没有在线持有者。
- **同一次断线检验**：同一套脚本分别跑 `takeover` 与 `wait`，逐条对照六项检查。

顶栏还可以切换「旧实例重新上线 / 永不再回来」——这正是两种交接策略分出胜负的地方。

## 设计

### API Server（`src/apiserver.js`）

- 每次写都推进全局 `resourceVersion`，事件按 rv 严格排序。
- `update` / `remove` 必须携带基础 rv，不匹配抛 `Conflict`（附当前对象）。
- 事件投递可暂停：写照常提交进日志，事件先排队；`step` 逐个放行，`resume` 整批放行。
  `step({ forId, rv })` 可指定只投给某个实例、指定版本，用来复现「删除先到、迟到的创建后到」。
- **墓碑**：删除时记下该 key 的 epoch，之后 `create` 的 epoch 不大于墓碑就拒绝。
  旧实例断线前发出的创建迟到时，不会复活已删除的对象。
- **epoch 栅栏**：`update` 可带 `(owner, epoch)`，与服务器当前持有者不符就拒绝。

### 控制器（`src/controller.js`）

三条不变量：

| 不变量 | 做法 |
|---|---|
| 旧事件不复活对象 | 只应用 rv 严格递增的事件；删除后迟到的创建被丢弃 |
| 不双写 | 每次写入带基础 rv；冲突用服务器返回的 rv 乐观重试 |
| 归宿明确 | 接管策略下写入带 epoch 栅栏；被拒即销账并写入台账 |

领取规则（`shouldClaim`）：

- 无主任务：由仍然在线的实例领取。
- `wait`（直接等待）：从不碰旧实例名下的任务。
- `takeover`（新实例接管）：`epoch` 更高的实例直接接管；同世代只有租约过期才接。

断线只关闭 watch、保留本地记忆；重连从本地最后的 rv 续订，**不重新列举**——缓存可能过期，
正确性由服务器端 CAS 和 epoch 栅栏保证，而不是本地记忆。

### 判定（`src/invariants.js`）

审计只看服务器写入日志和最终状态，不信控制器的自述：

- `live-owner`：每个未完成任务在服务器上的持有者必须是在线实例，且在线实例中恰有一个声称持有它。
- `no-double`：任何一次推进工作量的写入，写作者、写前持有者、写后持有者必须一致。
- `no-epoch-regress`：同一 key 被接受的写入，epoch 不得回退。
- `no-resurrection`：同一 key 出现 `delete` 之后，不得再出现 `create`。
- `ledger-resolved`：在线实例的台账不得有未决项。

### 同一次断线检验（`src/drill.js`）

两种策略跑**完全相同**的脚本，唯一变量是领取规则：

1. `old@1` 持有 `task/a`、`task/b`，干了一部分活。
2. 暂停事件投递。
3. `old` 发出 `create task/ghost` 后断线。
4. 管理员删除 `task/ghost`、删除 `task/b`、新建 `task/c`。
5. `new@2` 从旧检查点续订（不列举），队列里同时有旧创建与新删除。
6. 按 rv 逆序只投给 `new`：先 4 号删除、后 3 号创建。`new` 丢弃旧创建，ghost 不复活。
7. `new` 列举并接管；`old` 带着过期缓存重连，先做一次在途写入再重新列举。
8. 审计最终持有者与台账。

结果：

| 场景 | takeover | wait |
|---|---|---|
| 旧实例重新上线 | 旧实例写入被栅栏拒绝，`task/a → new@2` | 旧实例自己收回 `task/a`，但接管前有一个无人持有窗口 |
| 旧实例永不再回来 | `task/a → new@2`，全部完成 | `task/a` 留在 `old@1` 名下，无人执行，审计不通过 |

两种策略都**不复活对象、不双写**；差别只在「旧实例不回来时，活还有没有执行者」。
所以，同一次断线检验能保持**有且只有一个资源所有者**的，是让新实例接管（`takeover`）。

## 目录

```
src/apiserver.js   模拟 API Server：list / watch / CAS / 墓碑 / 栅栏 / 暂停投递
src/controller.js  控制器实例：事件应用、领取、干活、交接台账
src/invariants.js  不变量审计
src/drill.js       同一次断线检验的故障脚本
public/            页面（无框架，原生 ES modules）
scripts/serve.js   静态服务器
scripts/drill-cli.js  命令行检验
test/              Node 内置 test runner
```
